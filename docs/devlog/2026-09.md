## 2026-09-26 - Stage native Web and TUI in one Workbench profile

### Result

- The candidate workbench profile now stages the native DSH Web bundle and a
  Workbench-built Web plugin beside the pinned TUI and patched DSH closure
  before runtime-kit setup. The plugin archive must match a reviewed canonical
  SHA-256 in the separate Web artifact record before profile creation. Workbench
  `v0.1.0-rc.6` binds that record to the release identity in the compare gate.

### Why / context

- The previous browser acceptance and combined TUI setup used separate
  profiles, so they did not prove that both interfaces could share one governed
  installed graph. Checking only the Web package name and version would allow
  changed Client code under the same identity; the recorded digest closes that
  gap without a hash cycle with the embedded contract identity. The compare
  gate also rejects a changed or newly added digest at an unchanged release
  version.

### Evidence

- A new regression failed against the prior TUI-only profile. A second
  regression showed that altered Client bytes under the same Web name and
  version initially passed staging, then failed after digest enforcement.
  A third regression showed that a digest change or first record addition
  could pass the release comparison without a version bump, then failed after
  the compare gate was extended. Web package build, pack, and archive
  inspection, 39 Workbench tests, typecheck, publication scan, and comparison
  with the prior release passed locally. Hosted CI remains pending.

### Links

- <https://github.com/sympoies/dsh-workbench/issues/5>

### Follow-ups

- Hosted Linux x64 and macOS arm64 strict graph installation and runtime-kit
  composition must pass before claiming the combined profile; browser and
  governed Bash acceptance remain separate gates.
